- [ ] **`@team` fanout skips the sending handle, so the machine with the problem is the one that cannot hear its own alert** — `fanout.ts:106` does `if (handle === e.from) continue`. That is right for humans talking (nobody wants their own broadcast back) and wrong for a machine paging the fleet: an automated checker on host X broadcasts a finding about host X, and every session ON host X — the ones that could act on it — is the only audience excluded. Surfaced 2026-08-31 by a peer whose `refwatch` alert reached three other boxes and none of its own three sessions. Confirmed live the same evening by two independent lines of evidence, neither of them code reading: a peer reported that **none of the five `@team` broadcasts it sent that day came back to any session on its own host** (`msg_01M1C3P8KQ`), and a sibling session on this box shipped a self-delivery workaround whose payload states the behaviour outright — *"(local copy: the fleet-wide broadcast does not come back to this host.)"* It was initially missed because a second fault (the checker's `fleet` was absent from the systemd user PATH, so it never sent at all) fully accounted for the same empty value and masked this one; a peer consequently retracted the hypothesis as disproven, then withdrew the retraction. Worth keeping as a diagnostic note: two independent sufficient causes were stacked, the outer one explained every observation, and elimination therefore ruled out a mechanism plainly present in the code. Note the diagnostic trap for whoever picks this up: two independent sufficient causes were stacked, and the outer one explained every observation, so elimination gave the wrong answer. Scope is a semantic decision, not a one-line change: one flag currently serves both meanings. Candidates — an opt-in `echo_to_sender` meta, a separate kind for machine-generated alerts, or leaving fanout alone and having such tools also deliver locally (relates to the unrecorded `fleet local send` gap).  (size: M)
