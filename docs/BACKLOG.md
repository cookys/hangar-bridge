## Open
- [ ] **`@team` fanout skips the sending handle, so the machine with the problem is the one that cannot hear its own alert** — `fanout.ts:106` does `if (handle === e.from) continue`. That is right for humans talking (nobody wants their own broadcast back) and wrong for a machine paging the fleet: an automated checker on host X broadcasts a finding about host X, and every session ON host X — the ones that could act on it — is the only audience excluded. Surfaced 2026-08-31 by a peer whose `refwatch` alert reached three other boxes and none of its own three sessions. **Not yet observed live**, because a second fault (the checker's `fleet` was absent from the systemd user PATH, so it never sent at all) fully accounted for the same empty value and masked this one; the peer consequently retracted the hypothesis as disproven. It is not disproven — it is the next layer, and fixing the PATH will expose it. Note the diagnostic trap for whoever picks this up: two independent sufficient causes were stacked, and the outer one explained every observation, so elimination gave the wrong answer. Scope is a semantic decision, not a one-line change: one flag currently serves both meanings. Candidates — an opt-in `echo_to_sender` meta, a separate kind for machine-generated alerts, or leaving fanout alone and having such tools also deliver locally (relates to the unrecorded `fleet local send` gap).  (size: M)
- [ ] **`repo` derivation collapses local bare-remote layouts to the literal `origin`** — `roots.ts` takes the last path segment of `remote.origin.url`, which is right for `…/owner/name.git` but wrong for the common local-bare layout `~/projects/<project>/origin.git`, where the project name sits in the second-to-last segment. Observed live on the cuda box: a session in `~/projects/fighter/qwen3.8-27b` reports `repo: "origin"`. This stopped being cosmetic when `to_filter --repo` shipped: that session cannot be reached by `--repo fighter`, and any other box using the same layout collapses into one shared `origin` group, turning `--repo origin` into an unintended broadcast. Candidate fixes (each with tradeoffs, none validated): walk up a segment when the basename is `origin`/`.git`, or derive from `git rev-parse --show-toplevel` instead of the remote. No survey of the fleet's actual remote layouts exists yet.  (size: S)
- [ ] **presence heartbeats must not enter the durable message buffer** — every presence_update is an `@team` broadcast, so `presence.ts:51` INSERTs it; measured 2026-08-31, presence is **99.3% of the last two hours' rows** (8301 vs 59 substantive). That makes `poll_inbox` — the pull mainline this project gives non-Claude harnesses — effectively unusable: a peer reports having to page through many screens of `(connected)` to reach real messages, so it can only prove the link is alive, not check for missed traffic. The earlier fix absorbed presence on the RECEIVING side only; the sending side was never touched. Note the volume is not anyone flapping: intervals are a clean 30s heartbeat, and totals track the number of concurrent agent sessions per box (each opens its own peer-agent under the shared handle). An ephemeral path already exists for `to_filter` chat — scope is deciding whether presence is a "message" at all, not building new machinery.  (size: L)
- [ ] **ephemeral messages have no working reply path** — `messages.ts:168` tells the receiver to reply via `meta.correlation_id` instead of `in_reply_to` (which 400s on an unknown parent), but nothing ever generates one: the relay strips a sender-supplied `correlation_id` at `:108` as anti-forgery, and the ephemeral branch at `:169` sets only `ephemeral='1'`. So both routes are closed and the receiver can only open a new, thread-less message. Reported first-hand by a peer that hit the 400. The comment describes a contract that is not implemented.  (size: S)
- [ ] **sibling processing rights are unassigned** — a durable row is `poll_inbox`-visible to every session sharing the handle (by design, so nobody misses traffic), but N sessions may each answer it. It has not caused duplicate replies yet, and the peer that reported it was explicit about why: *"重複回覆沒發生過，不代表機制存在 — 今天兩次都是人為介入補上的."* Two candidate shapes, neither adopted: **pre-emptive** (claim the thread; needs a registration habit that the 2026-08-31 hardware-claim episode showed is hard to establish) and **assigned** (one session holds the handle's inbox role, others speak only with new information; worked that day only because an operator named the holder).
